Personal Financial Operating System — Frontend Build Prompt
Build a premium, mobile-first personal financial operating system as a Progressive Web App (PWA).

This is initially a private, single-user financial management system designed for one person. However, architect the frontend and data structures cleanly enough that the product can later evolve into a multi-user fintech startup.

The application should NOT initially be presented as a bank. It is a personal financial operating system that helps the user automatically allocate incoming money into purpose-based financial pools, control how those pools can be spent, track every financial transaction, manage savings goals, and understand their overall financial behavior.

The product should feel like a premium Nigerian fintech application.

Use modern Nigerian fintech applications such as Kuda and OPay as UX inspiration only. Study their current mobile navigation patterns, information hierarchy, transaction presentation, balance visibility, quick actions, savings presentation, notification patterns, spacing and interaction design. Do NOT copy their visual identity, layouts, assets, logos, illustrations or exact components.

Kuda’s current app emphasizes a clean home screen, quick access to common financial actions, search, savings/investments, account actions and notifications. OPay emphasizes a financial dashboard, transfers, savings, balance privacy and transaction activity. Use these as UX references while creating a completely original product identity.

Core Product Concept
The central idea is:

“Every naira should have a job.”

When money enters the user’s financial account, the system automatically distributes that income across predefined financial pools according to the user’s allocation policy.

Example:

Income received: ₦500,000

Needs: 40%
Savings: 15%
Emergency: 10%
Learning: 7%
Investment: 10%
Fun: 8%
Giving: 5%
Flexible: 5%

The user should not have to manually perform these allocations.

The application should calculate and display them automatically.

The initial allocation policy will be supplied separately and must be treated as the default configuration. Do not invent the final percentages or policy rules.

The system must be designed so the user can later modify percentages, create pools, delete pools, change pool restrictions, create new allocation policies and configure different policies for different income sources.

Product Philosophy
The application should not feel like a traditional budgeting application.

It should feel like a personal financial control system.

The user should be able to open the app and immediately understand:

How much money exists
How much is actually available to spend
How much is reserved
What each portion of the money is meant for
What financial goals are currently active
What happened recently
Whether the user’s financial behavior is following their plan
The interface should make financial discipline feel effortless.

ARCHITECTURE
Keep the frontend cleanly separated from financial logic.

Do not calculate important financial state independently in random UI components.

Use a centralized financial state/domain layer.

The backend will eventually be responsible for:

Ledger
Allocation engine
Transaction validation
Pool policies
Payment provider integration
Webhook processing
Withdrawal execution

The frontend should consume these through clean interfaces.

For the initial frontend prototype, mock data may be used, but structure it exactly like real API data.

Do not hardcode fake balances directly inside UI components.

PAYMENT PROVIDER
The eventual payment provider is Paystack.

Do not hardwire Paystack-specific behavior into the UI.

Create provider-agnostic financial interfaces.

The frontend should eventually support:

Incoming payment
Payment confirmation
Account information
Transfer
Withdrawal
Transaction status
Provider reference

Paystack should be treated as the financial infrastructure layer, not the financial rules engine.
